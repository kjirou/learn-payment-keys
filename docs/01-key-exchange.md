# 01. 鍵交換: LMK, ZMK(ZCMK), KCV, key-under-key

## 登場する鍵

| 鍵 | 役割 |
|---|---|
| LMK (Local Master Key) | HSM 内部に格納される最上位の鍵。HSM の外に出ることはなく、HSM に保管する他のすべての鍵は LMK で暗号化された形で外部(DB など)に保存される。 |
| ZMK (Zone Master Key) / ZCMK (Zone Control Master Key) | 2 組織の間(ゾーン)で共有するマスター鍵。作業鍵(ZPK など)をこの鍵で暗号化して相手に渡す。一般には KEK (Key Encryption Key) と呼ばれる。 |
| 作業鍵 (Working Key) | 実際にデータを暗号化する鍵。ZPK、PVK、CVK など。ZMK によって運ばれる。 |

ZMK と ZCMK は同じ概念で、Thales payShield 系の呼び名が ZMK、VisaNet 系の呼び名が ZCMK。

## ZMK の受け渡し: 鍵コンポーネント

ZMK 自体は上位の鍵で暗号化できない(それが最上位だから)ので、人手で安全に受け渡す。慣例は次のとおり。

1. ZMK を 2〜3 個の **コンポーネント**(同じ長さのランダム値)に分割する。全コンポーネントの XOR が ZMK になる。
2. 各コンポーネントを別々の鍵管理者(custodian)が封緘して保持・輸送する。
3. 相手側 HSM に各管理者が自分のコンポーネントだけを入力し、HSM 内部で XOR して ZMK を復元する。

誰か 1 人だけでは鍵全体を知り得ない(デュアルコントロール、スプリットナレッジ)。

```
ZMK = component_1 XOR component_2 [XOR component_3]
```

## KCV (Key Check Value)

鍵の値を見せずに「同じ鍵を持っているか」を確認する値。

```
KCV = 3DES_key( 00 00 00 00 00 00 00 00 ) の先頭 3 バイト(6 桁の 16 進)
```

コンポーネントの受け渡しや鍵の登録のたびに KCV を照合し、入力ミスや取り違えを検出する。コンポーネントごとにも KCV を付ける。

## key-under-key: 作業鍵を ZMK で運ぶ

ZMK が共有できれば、以後の作業鍵はオンラインで交換できる。

```
ZPK under ZMK = 3DES_ZMK( ZPK )
```

送り側は ZPK を ZMK で暗号化し、KCV を添えて送る。受け側は ZMK で復号して ZPK を得て、KCV を照合する。この一連の処理はすべて HSM 内で行われ、平文の ZPK はアプリケーションにも見えない。HSM に入った鍵は、以後 LMK で暗号化された形(ZPK under LMK)で保管される。

```
相手組織                          自組織
ZPK under ZMK  ── ネットワーク ──▶ HSM: ZMK で復号 → LMK で再暗号化 → ZPK under LMK を DB に保存
```

## 鍵ブロック(TR-31 / Thales Key Block)

上の「鍵を単純に 3DES で暗号化する」形式は **バリアント方式** と呼ばれ、暗号化された鍵の用途(PIN 用か、鍵運搬用か)が暗号文からは分からないという弱点がある。これを突いた鍵の用途すり替え攻撃への対策として、鍵の用途・アルゴリズム・エクスポート可否などのヘッダーを付け、全体に MAC をかけた **鍵ブロック**(ANSI X9 TR-31、後の X9.143)が標準となった。PCI PIN 要件でも鍵ブロックの使用が求められている。

本リポジトリの実装はバリアント方式の最も単純な形(ヘッダーなしの 3DES ECB)で、概念理解のためのもの。

## 補足: DES 鍵のパリティ

DES 鍵の各バイトは最下位ビットがパリティビットで、奇数パリティに揃える慣習がある。DES のアルゴリズム自体はこのビットを無視するため、パリティを直しても暗号結果は変わらない。HSM はパリティの合わない鍵を拒否することが多い。
