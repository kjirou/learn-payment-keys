# 01. 前提知識: DES / 3DES, ECB, 記法

この章は、以降の章に出てくる `3DES_key( data )` のような式を読むための最低限の暗号の前提知識をまとめたもの。暗号アルゴリズムの内部構造(S-box や Feistel 構造)には踏み込まない。

## ブロック暗号

決済で使う対称鍵暗号は **ブロック暗号** で、固定長のデータ(ブロック)を鍵で別の固定長データに変換する。同じ鍵で逆変換(復号)できる。

```
暗号化: C = E_K( P )      P: 平文ブロック, K: 鍵, C: 暗号文ブロック
復号:   P = D_K( C )
```

DES / 3DES のブロック長は **8 バイト(64 ビット)**。本リポジトリで扱うデータが 8 バイト単位になっている(PIN ブロック 8 バイト、ARQC 8 バイト、16 バイト鍵は 8 バイト × 2)のはこのため。

## DES (Data Encryption Standard)

1977 年に米国標準となったブロック暗号。

| 項目 | 値 |
|---|---|
| ブロック長 | 8 バイト |
| 鍵長 | 8 バイト。ただし各バイトの最下位ビットはパリティビットで、実効 56 ビット |

56 ビットは 1990 年代末には専用ハードウェアで総当たりできる長さになった。しかし DES 前提の端末・HSM・仕様が世界中の決済網に広まっていたため、アルゴリズムを置き換える代わりに DES を 3 回重ねて延命したのが 3DES である。

## 3DES (Triple DES)

DES を「暗号化、復号、暗号化」の順に 3 回かける(EDE: Encrypt-Decrypt-Encrypt)。

```
暗号化: C = E_K3( D_K2( E_K1( P ) ) )
復号:   P = D_K1( E_K2( D_K3( C ) ) )
```

### 2-key と 3-key

| 方式 | 鍵の構成 | 鍵長 | 決済での呼び名 |
|---|---|---|---|
| 2-key 3DES | K1, K2, K1(K3 = K1) | 16 バイト(112 ビット) | ダブルレングス鍵 |
| 3-key 3DES | K1, K2, K3 | 24 バイト(168 ビット) | トリプルレングス鍵 |

決済業界で単に「3DES 鍵」と言えば、ほとんどの場合 **2-key の 16 バイト** を指す。ZMK、ZPK、PVK、IMK、UDK、セッション鍵はすべてこれで、本リポジトリの `tdesEncrypt` も 16 バイト鍵を受け取る。Go の標準ライブラリは 24 バイトを要求するので、`go/tdes.go` では K1 を末尾に複製して (K1, K2, K1) として渡している。

### 真ん中が「復号」である理由

K1 = K2 = K3 = K のとき、`E_K( D_K( E_K( P ) ) ) = E_K( P )` となり、3DES は単一 DES と同じ結果になる。3DES 対応の装置が旧来の単一 DES の相手とも通信できるようにするための設計である。

2-key で K1 = K2 = K とした場合も同じことが成り立つ。本リポジトリの JS 版は、Node(OpenSSL 3)が単一 DES の `des-ecb` を既定で提供しないため、この性質を使って単一 DES を「K || K の 3DES」として計算している。

```
鍵 K = 0123456789ABCDEF、平文 = 00 00 00 00 00 00 00 00 のとき

単一 DES_K            : D5D44FF720683D0D
3DES_(K||K)           : D5D44FF720683D0D   ← 同じ
3DES_(K||FEDCBA9876543210) : 08D7B4FB629D0885   ← K2 が違えば別の値
```

### 単一 DES が残っている場所

3DES の時代になっても、アルゴリズムの一部として単一 DES がそのまま使われている箇所がある。

- **CVV**: CVK A と CVK B を別々の単一 DES 鍵として使う(`DES_CVKA`、`DES_CVKB^-1`)。
- **Retail MAC**(ARQC の計算): 鍵の左 8 バイトで単一 DES CBC を回し、最後だけ右 8 バイトを使う。

式の添字が `3DES_` か `DES_` かで、16 バイト鍵の 3DES か 8 バイト鍵の単一 DES かを区別している。

## ECB モード

8 バイトより長いデータを暗号化するとき、ブロックをどうつなぐかを **モード** という。

**ECB (Electronic Codebook)** は、各ブロックを独立に同じ鍵で暗号化する最も単純なモード。

```
C1 = E_K( P1 ),  C2 = E_K( P2 ),  ...
```

同じ平文ブロックは同じ暗号文ブロックになるため、一般のデータ暗号化には向かない(パターンが漏れる)。

```
鍵 0123456789ABCDEF FEDCBA9876543210 で "AAAAAAAAAAAAAAAA"(0x41 × 16)を暗号化:
A2C82014EA17457B A2C82014EA17457B   ← 2 ブロックが同じ
```

それでも決済の鍵階層で ECB が使われるのは、暗号化する対象が **鍵そのもの(16 バイト = 2 ブロック)や PIN ブロック(1 ブロック)** のようなランダムで短いデータであり、パターン漏洩が問題にならないため。`3DES_ZMK( ZPK )` は、ZPK の前半 8 バイトと後半 8 バイトを ECB で別々に暗号化している。

**CBC (Cipher Block Chaining)** は前のブロックの暗号文を次の平文に XOR してから暗号化するモードで、Retail MAC の内部で使われている(`docs/04-emv-keys.md`)。

## 本リポジトリでの記法

| 記法 | 意味 |
|---|---|
| `3DES_K( X )` | 16 バイト鍵 K で X を 2-key 3DES ECB 暗号化する。X は 8 バイトの倍数 |
| `3DES_K^-1( X )` | 同じく復号 |
| `DES_K( X )` | 8 バイト鍵 K で X を単一 DES 暗号化する |
| `DES_K^-1( X )` | 同じく復号 |
| `A XOR B`、`A ⊕ B` | 同じ長さのバイト列のビットごとの排他的論理和(`docs/02-key-exchange.md` 参照) |
| `A \|\| B` | バイト列の連結 |
| `K_L`, `K_R` | 16 バイト鍵の左 8 バイト、右 8 バイト |

## パディング

ブロック暗号はブロック長の倍数しか処理できないので、端数のデータには詰め物(パディング)をする。本リポジトリで出てくるのは次の 2 種類。

- **鍵と PIN ブロック**: もともと 8 バイトの倍数なのでパディングなし。
- **Retail MAC(ISO/IEC 9797-1 パディング方式 2)**: データの末尾に `80` を 1 バイト付け、その後ろを `00` で 8 バイトの倍数まで埋める。データがちょうど 8 バイトの倍数でも必ず `80 00 .. 00` の 1 ブロックを足す。

## 鍵のパリティ

DES 鍵の各バイトは、1 のビットの数が奇数になるように最下位ビットを調整する慣習がある(奇数パリティ)。DES のアルゴリズムはこのビットを無視するので暗号結果には影響しないが、HSM はパリティの合わない鍵を入力エラーとして拒否することが多い。EMV の鍵派生で最後に「奇数パリティ調整」が入るのはこのため。`adjustOddParity` が実装。

## 3DES の現在地

NIST は 3DES を 2023 年末で非推奨、2030 年末で使用終了としている。決済業界でも AES への移行が進んでおり、次のような AES 版の仕様が整備されている。

- TR-31 / X9.143 の AES 鍵ブロック
- ISO 9564 Format 4(AES、16 バイトの PIN ブロック)
- EMV の AES 版クリプトグラム・セッション鍵派生

ただしカードや端末の寿命が長いため 3DES はしばらく現役で、仕様を学ぶ出発点としては 3DES が中心になる。本リポジトリも 3DES のみを扱う。
